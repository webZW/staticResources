## 引言  

本白皮书探讨了**会话（Sessions）**与**记忆（Memory）**在构建有状态、智能化的大语言模型（LLM）代理中的关键作用，旨在帮助开发者创建更强大、个性化且具备持续性的AI体验。为了让大语言模型能够记忆信息、持续学习并实现交互个性化，开发者必须在其上下文窗口中动态地组织和管理信息——这一过程被称为**上下文工程（Context Engineering）**。

本文档的核心概念总结如下：

- **上下文工程（Context Engineering）**：  
  指在大语言模型的上下文窗口内动态组装和管理信息的过程，以实现具备状态记忆和智能行为的代理。

- **会话（Sessions）**：  
  用于容纳用户与代理之间完整对话的容器，记录对话的时间顺序历史以及代理的工作记忆。

具备状态记忆和个性化的AI体验，始于上下文工程。

## • 记忆（Memory）  
记忆是一种用于长期持久化的机制，能够跨多个会话捕捉并整合关键信息，为大语言模型（LLM）智能体提供持续且个性化的体验。

## 上下文工程（Context Engineering）

LLM本质上是无状态的。除了其训练数据之外，它们的推理和认知能力仅限于单次API调用中的“上下文窗口”内所提供的信息。这带来了一个根本性问题：AI智能体必须具备操作指令，明确可执行的动作、用于推理的事实证据数据，以及定义当前任务的即时对话信息。

为了构建有状态、智能化的智能体，使其能够记住信息、持续学习并实现交互个性化，开发者必须在每一次对话轮次中主动构建这种上下文。这种对LLM所需信息进行动态组装与管理的过程，被称为**上下文工程**。

上下文工程代表了从传统**提示工程（Prompt Engineering）** 的演进。提示工程侧重于设计最优的、通常是静态的系统指令；而**上下文工程**则关注整个输入负载（payload），基于用户身份、对话历史和外部数据，动态地构建一个具备状态感知能力的提示。

它涉及策略性地选择、摘要和注入不同类型的信息，在最大化相关性的同时最小化噪声干扰。大量上下文由外部系统管理，例如：  
- RAG数据库  
- 会话存储（Session Stores）  
- 记忆管理系统（Memory Managers）

智能体框架必须协调这些系统，以检索并将上下文整合成最终的提示。

可以把上下文工程比作烹饪中的**“mise en place”**——即厨师在开始烹饪前，预先准备好所有食材的关键步骤。如果你只给厨师一份菜谱（提示），他们可能只能用手边随机找到的材料做出一顿普通的饭菜；但如果你先确保他们拥有所有正确且高质量的食材，并经过精心准备，那么最终呈现的将是一道卓越的佳肴。

通过精心设计的工具组合以及对呈现风格的清晰理解，上下文工程能够可靠地生成出色且高度定制化的结果。其核心目标是确保模型所拥有的信息**恰到好处**——不多不少，仅包含完成任务最相关的上下文内容。

上下文工程负责构建一个复杂的输入载荷（payload），该载荷可包含多种组件：

## • 用于引导推理的上下文  
定义智能体的基本推理模式和可用操作，从而决定其行为方式：

- **系统指令（System Instructions）**  
  高层次的指导方针，用于定义智能体的角色、能力范围及限制条件。

- **工具定义（Tool Definitions）**  
  API 或函数的结构化描述，使智能体能够调用外部资源进行交互。

- **少量示例（Few-Shot Examples）**  
  精心挑选的实例样本，通过上下文学习（in-context learning）引导模型的推理路径。

## • 证据性与事实性数据  
这是智能体进行推理的实际依据，包括先验知识和为特定任务动态获取的信息，作为其回应的“证据”基础：

- **长期记忆（Long-Term Memory）**  
  跨多个会话积累的关于用户或主题的持久化知识。

- **外部知识（External Knowledge）**  
  从数据库或文档中检索得到的信息，通常借助**检索增强生成**（Retrieval-Augmented Generation, RAG）技术实现。

- **工具输出（Tool Outputs）**  
  工具执行后返回的数据或结果。

- **子智能体输出（Sub-Agent Outputs）**  
  被委派特定子任务的专业化智能体所返回的结论或结果。

## 9 大上下文要素  

- **人工制品（Artifacts）**：与用户或会话相关的非文本数据（例如文件、图像）。  
- **即时对话信息**：使智能体能够立足于当前交互，明确当前任务，包括：  
  - **对话历史（Conversation History）**：当前交互的逐轮对话记录。  
  - **状态 / 草稿区（State / Scratchpad）**：智能体在即时推理过程中使用的临时性、进行中的信息或计算结果。  
  - **用户提示（User's Prompt）**：需要立即响应的当前查询。  

## 动态上下文构建的重要性  

上下文的动态构建至关重要。例如，记忆并非静态存在；必须根据用户与智能体的互动或新数据的摄入，进行选择性检索和更新。此外，有效的推理通常依赖于**上下文学习**（in-context learning）——即大语言模型通过提示中的任务示例来学习如何执行任务。当智能体使用与当前任务相关的**少样本示例**（few-shot examples）时，这种学习方式比依赖硬编码示例更为高效。  

同样，RAG（检索增强生成）工具会基于用户的即时查询，动态检索外部知识。  

## 核心挑战：不断增长的对话历史  

构建具备上下文感知能力的智能体面临的关键挑战之一，是管理持续增长的对话历史。理论上，具有大上下文窗口的模型可以处理长篇对话记录；但在实践中，随着上下文的增长，计算成本和响应延迟也随之上升。更严重的是，模型可能出现“**上下文衰减**”（context rot）现象——即随着上下文长度增加，模型对关键信息的关注能力逐渐下降。  

## 上下文工程的应对策略  

**上下文工程**（Context Engineering）通过动态调整对话历史来直接应对这一挑战，例如采用以下策略：  
- 对话内容**摘要化**（summarization）  
- **选择性剪枝**（selective pruning）  
- 其他**压缩技术**（compaction techniques）  

这些方法在控制总 token 数量的同时，保留了关键信息，最终实现更稳健、更个性化的AI交互体验。

## 4. 上传上下文  
在当前轮次中收集到的新信息会被上传至持久化存储。这一过程通常是“后台”进行的，允许智能体在内存整合或其他后续处理异步执行的同时完成当前任务。

在整个生命周期的核心，有两个基本组成部分：**会话（Sessions）** 和 **记忆（Memory）**。  
- **会话** 管理单次对话中逐轮交互的状态。  
- **记忆** 则提供长期持久化的机制，用于跨多个会话捕获并整合关键信息。

你可以将“会话”想象成你为某个特定项目所使用的办公桌或工作台。  
当你正在工作时，桌面上摆满了所需的工具、笔记和参考资料——所有内容都触手可及，但这些也都是临时性的，仅服务于当前任务。  

一旦项目结束，你不会把整张杂乱的工作台直接塞进仓库保存。相反，你会开始“构建记忆”的过程——这就像整理一个有序的文件柜。你回顾桌上的材料，丢弃草稿和重复的笔记，只将最关键、最终确定的文档归档到贴好标签的文件夹中。

这样，文件柜就能始终保持整洁、可靠且高效，成为未来所有项目的可信知识来源，而不会被工作台上的短暂混乱所污染。

这个类比准确地反映了高效智能体的运作方式：  
- **会话** 是单次对话的临时工作台；  
- **记忆** 则是精心组织的文件柜，使智能体在未来交互中能够回溯关键信息。

在上述对上下文工程的高层次概述基础上，我们现在可以进一步探讨两个核心组件：**会话** 与 **记忆**，首先从 **会话** 开始。

### 会话（Sessions）

会话是上下文工程中的一个基础元素，它封装了单次连续对话的即时对话历史和工作记忆。每个会话都是与特定用户关联的独立记录，使智能体能够在一次对话范围内保持上下文并提供连贯的响应。

一个用户可以拥有多个会话，但每一个会话都代表一次独立且相互隔离的交互日志。每个会话包含两个关键组成部分：**按时间顺序排列的历史记录（events）** 和 **智能体的工作记忆（state）**。

#### 事件（Events）

事件是构成对话的基本单元。常见的事件类型包括：

- **用户输入**：来自用户的输入内容（如文本、音频、图像等）；
- **智能体响应**：智能体对用户的回复；
- **工具调用**：智能体决定使用某个外部工具或API的操作；
- **工具输出**：工具调用后返回的数据结果，智能体将据此继续推理。

这些事件共同构成了完整的对话流程，其结构类似于传递给Gemini API的 `Content` 对象列表——其中每个具有 `role` 和 `parts` 的条目，代表对话中的一轮交互，即一个“事件”。

#### 状态（State）

除了聊天历史外，会话通常还包含一个 **状态（state）** ——一种结构化的“工作记忆”或临时草稿区。该状态用于存储当前对话相关的临时结构化数据，例如购物车中包含的商品项。

随着对话的推进，智能体会不断向会话中追加新的事件，并可能根据内部逻辑更新或修改状态。这种动态演变使得智能体能够持续跟踪对话进展并做出更符合上下文的决策。

Agent 框架在你的代码与大语言模型（LLM）之间扮演着通用翻译器的角色。作为开发者，你在每次对话轮次中只需操作框架提供的统一、内部数据结构，而框架则负责将这些结构转换为 LLM 所需的精确格式。

这种抽象机制非常强大，因为它将 Agent 的逻辑与所使用的具体 LLM 解耦，避免了厂商锁定（vendor lock-in）问题。

## 图 2：Agent 的上下文管理流程

最终目标是生成一个 LLM 能够理解的“请求”。以 Google 的 Gemini 模型为例，该请求是一个 `List[Content]` 结构。每个 `Content` 对象类似于一个简单的字典，包含两个键：

- **role**：表示发言者身份（"user" 或 "model"）
- **parts**：表示消息的实际内容（文本、图像、工具调用等）

在发起 API 调用前，框架会自动将内部数据对象（例如 ADK 的 `Event`）映射为对应的 `role` 和 `parts` 字段，填入 `Content` 对象中。

本质上，框架为开发者提供了一个稳定、统一的内部 API，同时在后台处理不同 LLM 复杂且多变的外部接口差异。

## ADK 中的会话模型

ADK 使用一个显式的 **Session** 对象，该对象包含两个主要部分：

- 一个 **Event** 对象列表（用于记录对话历史）
- 一个独立的状态对象（state object）

可以把 Session 想象成一个文件柜：  
- 一个文件夹存放对话历史（events）  
- 另一个文件夹存放工作记忆（state）

这种设计将历史记录与运行时状态分离，结构清晰。

## LangGraph 的状态模型

LangGraph 并没有正式的“会话”（session）对象。相反，**状态即会话**。

这个全面的状态对象包含：
- 对话历史（作为 `Message` 对象的列表）
- 所有其他工作数据

与传统会话中仅能追加（append-only）的日志不同，LangGraph 的状态是**可变的**。这意味着它可以被修改和转换，并支持如**历史压缩**（history compaction）等策略来优化记录。

这一特性对于管理长对话和应对 token 限制非常关键。

## 多智能体系统中的会话

在多智能体系统中，多个智能体协同工作，每个智能体专注于特定的、较小的任务。为了高效协作，它们必须共享信息。

其中，一个核心组成部分是系统如何处理**会话历史**——即所有交互的持久化日志。这个共享的历史记录成为各智能体理解上下文、协调行动的基础。

# 上下文工程：会话与记忆  
**2025年11月17日**

在多智能体系统中，智能体框架通常采用两种主要方式之一来处理会话历史：**共享的统一历史记录**，即所有智能体共同维护一个单一的日志；或**独立的单独历史记录**，即每个智能体各自维护自己的视角。

选择哪种模式取决于任务的性质以及智能体之间期望的协作方式。

## 共享的统一历史记录

这种模式最适合需要紧密协作、依赖单一事实来源的任务，例如多步骤的问题求解流程——其中一个智能体的输出直接作为下一个智能体的输入。

即使使用共享历史记录，子智能体也可能在将日志传递给大语言模型（LLM）之前对其进行处理。例如，它可以过滤出相关事件的子集，或添加标签以标识每个事件由哪个智能体生成。

一种新兴的架构模式——**代理间通信（Agent-to-Agent, A2A）**，正在被用于协调这些孤立代理之间的协作。尽管该模式使代理能够交换消息，但它未能解决共享丰富上下文状态这一核心问题。每个代理的对话历史都以其框架内部的数据结构进行编码，因此任何包含会话事件的A2A消息都需要一个翻译层才能被有效使用。

一种更强大的互操作性架构模式是将共享知识抽象为与框架无关的数据层，例如 **Memory（记忆层）**。与仅保存原始、特定框架对象（如 Events 和 Messages）的 **Session（会话）存储** 不同，记忆层旨在存储经过处理的、标准化的信息。关键信息——如摘要、提取出的实体和事实——从对话中被提取出来，并通常以字符串或字典的形式存储。记忆层的数据结构不依赖于任何一个框架的内部数据表示，使其能够作为通用的共享数据层。这种模式使得异构代理可以通过共享一个共同的认知资源来实现真正的协同智能，而无需开发自定义的翻译组件。

## 2025年11月21日 安全与隐私  

保护会话中包含的敏感信息是一项不可协商的基本要求。

### 严格隔离

**严格隔离** 是最核心的安全原则。每个会话仅归属于单一用户，系统必须强制实施隔离机制，确保一个用户绝不能访问其他用户的会话数据（例如通过访问控制列表 ACL 实现）。对会话存储的每一次请求都必须经过身份验证，并基于会话所有者进行授权。

处理个人身份信息（PII）的最佳实践是在会话数据写入存储之前对其进行**脱敏或屏蔽**。这一基础性安全措施能显著降低潜在数据泄露的风险及其“影响范围”。通过确保敏感数据**从不持久化**——可借助如 **Model Armor 9** 等工具实现——不仅能简化对 GDPR、CCPA 等隐私法规的合规工作，还能增强用户信任。

### 数据完整性与生命周期管理

生产级系统必须明确会话数据在时间维度上的存储与维护规则。会话不应永久存在。可通过实施**生存时间（TTL）策略**，自动删除长时间未活跃的会话，从而控制存储成本并降低数据管理负担。

这要求制定清晰的数据保留策略，明确定义会话数据应保留多久后被归档或永久删除。

此外，系统必须保证操作以**确定性的顺序**追加到会话历史中。维持事件正确的时序关系，是保障对话日志完整性的根本前提。

## 2025年11月 22日 性能与可扩展性  

会话数据处于每次用户交互的“热路径”上，因此其性能是首要关注点。读取和写入会话历史必须极其迅速，以确保响应灵敏的用户体验。

代理运行时通常是无状态的，因此在每一轮对话开始时，整个会话历史都需从中央数据库中检索，这会带来网络传输延迟。

为减轻延迟，关键在于减少传输数据的大小。一个重要的优化措施是在将会话历史发送给代理之前，对其进行过滤或压缩。例如，可以移除那些对当前对话状态已不再相关的旧函数调用输出。

下一节将详细介绍多种压缩历史记录的策略，以有效管理长上下文对话。

## 管理长上下文对话：权衡与优化

在一种简单的架构中，会话是用户与代理之间对话的不可变日志。然而，随着对话不断延长，所使用的 token 数量也随之增加。尽管现代大语言模型（LLM）能够处理长上下文，但仍存在局限性，尤其对于对延迟敏感的应用：

1. **上下文窗口限制**  
   每个 LLM 都有其一次可处理的最大文本量（即上下文窗口）。如果对话历史超出此限制，API 调用将失败。

2. **API 成本（$）**  
   大多数 LLM 提供商根据你发送和接收的 token 数量计费。较短的历史意味着更少的 token，从而降低每轮的成本。

## 3. 延迟（速度）  

向模型发送更多文本需要更长时间处理，导致用户响应变慢。**压缩（Compaction）** 能让智能体保持快速和响应灵敏的体验。

## 4. 质量  

随着 token 数量增加，上下文中的“噪声”增多，以及自回归生成过程中可能出现的累积误差，模型性能可能下降。管理一个长对话的过程，可以类比为一位精明的旅行者为长途旅程打包行李箱——

- **行李箱**代表智能体有限的上下文窗口，  
- **衣物和物品**则对应对话中的各种信息片段。

如果试图把所有东西都塞进去，行李箱就会变得过重且杂乱，难以快速找到所需物品——正如上下文窗口超载会提高计算成本并拖慢响应速度。  
相反，如果装得太少，又可能遗漏关键物品，比如护照或保暖外套，从而影响整个旅程——就像智能体可能丢失重要上下文，导致回答不相关或错误。

无论是旅行者还是智能体，都面临相似的限制：**成功的关键不在于能携带多少，而在于只携带真正需要的东西。**

### 压缩策略的作用  

压缩策略通过缩小冗长的对话历史，将对话内容浓缩，使其适配模型的上下文窗口，从而降低 API 成本和延迟。随着对话持续进行，每轮发送给模型的历史记录可能变得过大。压缩策略通过智能裁剪历史内容，在尽可能保留关键上下文的同时解决这一问题。

---

- **保留最近 N 轮对话**：这是最简单的策略。智能体仅保留最近的 N 轮对话（即“滑动窗口”），丢弃更早的所有内容。

## 基于令牌的截断  
在将历史消息发送给模型之前，代理会从最近的消息开始向前计数令牌数量。它尽可能多地包含消息，但不超过预设的令牌限制（例如4000个令牌）。所有更早的消息将被直接截断丢弃。

## 递归摘要  
对话中较早的部分会被AI生成的摘要所替代。随着对话不断延长，代理会定期调用另一个大语言模型（LLM）来总结最古老的消息。该摘要随后作为历史记录的压缩形式，通常被前置到保留下来的近期原始消息之前。

例如，你可以通过为ADK应用使用内置插件的方式，在ADK中仅保留最近N轮对话，从而限制发送给模型的上下文内容。

### 代码片段3：使用ADK将会话截断为仅保留最近N轮

```python
        # 保留最近10轮对话以及最新的用户查询

```

- **基于计数的触发**（例如：token 数量或对话轮次阈值）

- **基于时间的触发**  
  压缩并非由对话长度触发，而是由用户活动缺失引发。例如，若用户在一段时间内（如15或30分钟）无交互，系统可在后台自动运行压缩任务。  

- **基于事件的触发**（例如：语义变化或任务完成）  
  当智能体检测到某项具体任务、子目标或对话主题已结束时，主动触发压缩。

### 记忆  

记忆与会话之间存在着深刻的共生关系：**会话是生成记忆的主要数据来源，而记忆则是控制会话规模的关键策略**。  

记忆是从对话或数据源中提取出的有意义信息的快照，是一种浓缩的表示形式，用于保留重要上下文，以便在未来的交互中使用。通常情况下，记忆会在多个会话之间持久化保存，从而提供连续且个性化的用户体验。

- **个性化**：最常见的应用场景是记住用户的偏好、事实以及过往互动，以定制未来的响应。例如，记住用户最喜欢的运动队或其偏好的飞机座位，可带来更贴心、更具个性化的体验。

### 记忆的类型  

代理（Agent）的记忆可以根据信息的存储方式和获取方式进行分类。这些不同类型的记忆协同工作，帮助系统更丰富、深入地理解用户及其需求。

在所有类型的记忆中，一个核心原则始终成立：**记忆是描述性的，而非预测性的**。  
“记忆”是由记忆管理器返回的一个原子化上下文单元，供代理作为上下文使用。

尽管具体的数据结构可能有所不同，但一条记忆通常包含两个主要组成部分：**内容（content）** 和 **元数据（metadata）**。

---

#### 内容（Content）

内容是从原始数据中提取出的记忆实质部分，例如会话中的原始对话文本。  
关键在于，内容设计为**框架无关**（framework-agnostic），采用简单数据结构，便于任何代理轻松读取和处理。

内容可以分为两种形式：

- **结构化记忆（Structured Memories）**  
  指以通用格式存储的信息，如字典或JSON对象。其模式通常由开发者定义，而非特定框架决定。  
  示例：  
  ```json
  {"seat_preference": "Window"}
  ```

- **非结构化记忆（Unstructured Memories）**  
  使用自然语言描述来捕捉一次交互、事件或主题的核心含义。  
  示例：  
  “该用户偏好靠窗座位。”

---

#### 元数据（Metadata）

元数据提供关于记忆本身的附加信息，通常以简单的字符串形式存储。  
常见的元数据包括：

- 记忆的唯一标识符（ID）
- 记忆所属用户的标识（“所有者” ID）
- 描述内容类别或数据来源的标签

这些信息帮助记忆管理系统高效地检索、过滤和组织记忆，从而支持更智能的上下文感知行为。

### 信息的类型  

除了基本结构之外，记忆还可以根据其所代表的知识本质进行分类。这种区分对于理解**智能体如何使用记忆**至关重要，它将记忆划分为两个主要功能类别，源自认知科学¹¹：  
- **陈述性记忆**（“知道是什么”）  
- **程序性记忆**（“知道怎么做”）

**陈述性记忆** 是指智能体对事实、数据和事件的知识。这类信息是可以被明确表达或“声明”的内容。如果某个记忆是对“什么”问题的回答，那么它就属于陈述性记忆。该类别包括：  
- 通用世界知识（语义记忆）  
- 特定用户相关信息（实体/情景记忆）

**程序性记忆** 则是智能体关于技能和工作流程的知识。它通过隐式地展示如何正确执行任务来指导智能体的行为。如果某条记忆有助于回答“如何”类的问题——例如预订旅行时正确的工具调用顺序——那它就是程序性记忆。

### 组织模式  

记忆创建之后，下一个关键问题是**如何组织它们**。记忆管理器通常采用以下一种或多种模式来组织记忆：  
- **集合（Collections）¹²**  
- **结构化用户画像（Structured User Profile）**  
- **滚动摘要（Rolling Summary）**

这些模式定义了单个记忆之间以及记忆与用户之间的关联方式。

## 集合模式  
**集合（Collections）** 模式将内容组织为针对单个用户的多个独立、自然语言形式的记忆单元。每条记忆代表一个独立的事件、摘要或观察结果，尽管同一高层主题下可能包含多条相关记忆。集合模式适用于存储和搜索与特定目标或主题相关的更大规模、结构较松散的信息池。

## 结构化用户画像  
**结构化用户画像（Structured User Profile）** 模式将以用户为核心的事实信息组织成一组稳定的资料，类似于一张持续更新的联系人卡片。该模式专为快速查询关键事实信息而设计，例如姓名、偏好设置和账户详情等。

## “滚动式”摘要  
与结构化用户画像不同，**“滚动式”摘要（Rolling Summary）** 模式将所有信息整合为单一、持续演进的记忆文档，以自然语言形式概括整个用户-智能体之间的交互关系。管理者不会创建新的独立记忆，而是不断更新这一主文档。此模式常用于压缩长时间的会话记录，在保留关键信息的同时有效控制总token数量。

## 存储架构  
此外，**存储架构** 是一项关键决策，直接影响智能体检索记忆的速度与智能化水平。架构的选择决定了智能体在查找概念相似内容、理解结构化关系，或两者兼备方面的能力表现。

记忆通常存储于 **向量数据库（vector databases）** 和/或 **知识图谱（knowledge graphs）** 中：

- **向量数据库** 有助于找到与查询在概念上相似的记忆。
- **知识图谱** 则将记忆表示为实体及其相互关系构成的网络，支持复杂的关系推理与结构化查询。

## 向量数据库

向量数据库是最常见的方法，能够基于语义相似性而非精确关键词进行检索。记忆内容被转换为嵌入向量，数据库则根据用户查询找出在概念上最接近的匹配项。这种方法在检索非结构化的自然语言记忆时表现优异，尤其适用于上下文和含义至关重要的场景（例如“原子事实”<sup>14</sup>）。

## 知识图谱

知识图谱用于将以实体（节点）及其关系（边）构成的网络形式存储记忆。检索过程涉及遍历该图谱，以发现直接或间接的关联，使智能体能够推理不同事实之间的联系。它非常适合处理结构化、关系型的查询，并深入理解数据内部复杂的连接关系（例如“知识三元组”<sup>15</sup>）。

还可以将两种方法结合，形成一种**混合方法**：在知识图谱的结构化实体中融入向量嵌入。这使得系统可以同时执行关系型检索和语义检索，兼具图谱的结构化推理能力与向量数据库细腻的概念搜索优势，实现两者的优势互补。

## 记忆生成机制

我们也可以根据记忆的创建方式进行分类，包括信息是如何被推导出来的。

- **显式记忆**：当用户明确下达指令让智能体记住某件事时创建（例如：“记住我的结婚纪念日是10月26日”）。
- **隐式记忆**：当智能体从对话中自动推断并提取信息，而无需用户直接命令时生成（例如：“我的结婚纪念日快到了，你能帮我给伴侣选个礼物吗？”）

## 内部记忆（Internal Memory）  
指直接内置于智能体框架中的记忆管理机制。这种方式便于快速上手，但通常缺乏高级功能。虽然内部记忆可以使用外部存储，但生成记忆的机制仍由智能体内部完成。

## 外部记忆（External Memory）  
指采用一个独立的、专门用于记忆管理的服务（例如 Agent Engine Memory Bank、Mem0、Zep）。智能体框架通过API调用该外部服务来实现记忆的存储、检索和处理。这种方法提供了更强大的功能，如语义搜索、实体抽取和自动摘要，将复杂的记忆管理任务交由专用工具处理。

## 记忆范围（Memory Scope）  
还需要考虑一条记忆所描述的对象——即这条记忆是关于“谁”或“什么”的。这会影响你选择以哪个实体（用户、会话或应用）为基础来聚合和检索记忆。

### 用户级范围（User-Level Scope）  
这是最常见的实现方式，旨在为每位用户提供连续且个性化的体验。例如：“该用户偏好中间座位。”  
此类记忆与特定的用户ID绑定，并在所有会话中持续存在，使智能体能够长期积累对该用户的偏好和历史行为的理解。

### 会话级范围（Session-Level Scope）  
主要用于压缩长对话内容。例如：“用户正在为2025年11月7日至11月14日之间从纽约到巴黎的行程购买机票，偏好直飞航班和中间座位。”

- **来源（source）**：生成记忆所依据的数据类型

**“用户表达了对最近发货延迟的不满。”**

这种方式确保了高效存储与上下文集成，同时避免了直接保留原始非文本数据所带来的隐私和性能问题。

## 深入探讨：记忆整合

在从冗长的对话中提取出记忆之后，**整合**过程应将新信息融入一个连贯、准确且持续演进的知识库中。这可以说是记忆生命周期中最复杂的阶段，它将一系列简单的事实集合转化为对用户的深度理解。如果没有整合机制，智能体的记忆很快就会变成一份嘈杂、矛盾且不可靠的日志，记录着所有曾经捕获的信息片段。

这种“自我整理”通常由大语言模型（LLM）管理，正是这一点使记忆管理系统超越了普通数据库的功能。整合解决了来自对话数据的几个根本性问题：

- **信息重复**：用户可能在不同对话中以多种方式提及同一事实（例如，“我需要订一张去纽约的航班”和后来的“我正在计划一次去纽约的旅行”）。若仅进行简单提取，就会生成两条冗余的记忆。
  
- **信息冲突**：用户的状态随时间变化。若缺乏整合，智能体的记忆中将保留相互矛盾的事实。

- **信息演化**：简单的事实可能逐渐变得更加丰富和具体。例如，最初的记忆“用户对市场营销感兴趣”可能会演变为“用户正领导一个专注于第四季度客户获取的营销项目”。

通过有效的整合，系统能够维护一个动态、精确并具有情境感知能力的用户画像，从而实现更智能、个性化的交互体验。

并非所有记忆都会长久保持有用。智能体必须进行**遗忘**——主动修剪那些过时、陈旧或置信度低的记忆，以确保知识库的相关性和高效性。遗忘可以通过以下两种方式实现：在信息整合过程中指示大语言模型（LLM）优先采用新信息，或通过设置“生存时间”（Time-to-Live, TTL）机制自动删除过期记忆。

**整合过程**是一种由LLM驱动的工作流，用于将新提取的洞察与用户已有的记忆进行比对。该流程分为三个主要步骤：

1. **检索相似记忆**  
   首先，系统尝试检索与新提取信息相似的已有记忆。这些记忆将成为潜在的整合候选对象。如果新信息与旧记忆相矛盾，则该旧记忆可能被删除；若能补充原有内容，则可能被更新。

2. **LLM分析决策**  
   接着，将已有记忆和新信息一并提交给LLM。其核心任务是联合分析两者，并判断应执行的操作。主要操作类型包括：
   - **UPDATE（更新）**：用新的或修正后的信息修改已有记忆。
   - **CREATE（创建）**：若新洞察完全新颖且与现有记忆无关，则创建一条新记忆。
   - **DELETE / INVALIDATE（删除/作废）**：若新信息使某条旧记忆变得完全无关或错误，则将其删除或标记为无效。

3. **执行记忆变更**  
   最后，记忆管理器将LLM的决策转化为一个事务操作，更新记忆存储系统。

这一闭环机制确保了记忆库始终动态、准确且精简，支持智能体长期有效地学习与适应。

为了评估可信度，智能体必须跟踪每个信息来源的关键细节，例如其**来源（源类型）**和**时效性（“新鲜度”）**。这些细节至关重要，原因有二：  
1. 它们决定了该来源在**记忆整合**过程中的权重；  
2. 它们影响智能体在推理过程中对该记忆的依赖程度。

**源类型**是决定可信度最重要的因素之一。数据来源主要分为以下三类：

- **引导数据（Bootstrapped Data）**：  
  来自内部系统预加载的信息，例如客户关系管理系统（CRM）。这类数据具有高可信度，可用于初始化用户的记忆，以解决“冷启动问题”——即当智能体首次接触某用户、尚无交互历史时，如何提供个性化体验的挑战。

- **用户输入（User Input）**：  
  包括用户显式提供的数据（例如通过表单提交，属于高可信度），或从对话中隐式提取的信息（通常可信度较低）。

- **工具输出（Tool Output）**：  
  来自外部工具调用所返回的数据。一般不建议基于工具输出生成长期记忆，因为此类记忆往往脆弱且容易过时，因此更适合用于短期缓存。

### 在记忆管理中考虑记忆谱系（Memory Lineage）

这种动态的、多源的记忆架构在管理记忆时带来了两个主要操作挑战：  
1. **冲突解决（Conflict Resolution）**

记忆整合过程中不可避免地会出现**冲突**——不同数据源提供的信息相互矛盾。此时，记忆的**来源追溯（provenance）** 能够帮助记忆管理器建立一个信任层级体系。当来自不同来源的记忆发生矛盾时，系统可根据源类型的可信度优先级进行裁决，保留更可靠的记忆版本。

当出现冲突时，智能体必须利用该层级结构制定冲突解决策略。常见的策略包括：优先考虑最可信的信息源、倾向最新信息，或寻找多个数据点之间的相互印证。

管理记忆的另一项挑战在于删除记忆。一条记忆可能源自多个数据源。当用户撤销对某一数据源的访问权限时，从该源派生出的数据也应被移除。然而，删除所有“接触过”该源的记忆可能过于激进。一种更精确但计算成本更高的方法是：仅使用剩余的有效数据源，从头重新生成受影响的记忆。

除了静态的来源信息外，记忆的可信度也应动态演化。当多个受信来源提供一致信息时，通过相互印证，记忆的置信度会提升。但一个高效的内存系统还必须主动整理已有知识，即进行**记忆修剪**——识别并“遗忘”那些不再有用的记忆。这种修剪可由多种因素触发：

- **基于时间的衰减**：记忆的重要性可能随时间推移而降低。例如，两年前的一次会议记忆很可能不如上周的会议相关。
- **低置信度**：若某条记忆基于薄弱推断形成，且从未被其他来源证实，则可能被剪除。
- **无关性**：随着智能体对用户的理解日益深入，它可能会判断某些陈旧、琐碎的记忆已不再符合用户当前目标。

通过结合**被动的记忆整合流程**与**主动的记忆修剪机制**，记忆管理器确保智能体的知识库不仅仅是不断累积的所有历史记录，而是一个经过精心筛选、准确且与用户高度相关的认知体系。

## 第52页：推理过程中的记忆谱系管理  

除了在整理语料库内容时考虑记忆的来源谱系外，在推理阶段也应评估记忆的可信度。智能体对某条记忆的信任程度不应是静态不变的；它必须随着新信息的获取和时间的推移而动态演化。  

信任度通过**佐证**得以提升——例如，当多个可信来源提供一致的信息时，相关记忆的置信度就会上升。相反，信任度会随着时间推移而**衰减**，因为旧记忆逐渐过时；同时，一旦出现矛盾信息，信任度也会下降。最终，系统可以通过归档或删除低置信度的记忆来实现“遗忘”。  

这种动态的信任评分机制在推理阶段至关重要。记忆及其对应的置信度通常**不会直接展示给用户**，而是被注入到提示词（prompt）中，使大语言模型（LLM）能够评估信息的可靠性，并做出更加细致、审慎的决策。  

整个信任框架服务于智能体的内部推理过程。记忆及其置信度作为隐式输入参与决策，帮助LLM权衡证据、判断信息来源的可靠性，从而提升输出结果的准确性和可信性。

## 触发机制

- **轮次节奏（Turn Cadence）**：在特定数量的对话轮次后运行记忆生成流程（例如，每5轮执行一次）。  
- **实时触发（Real-Time）**：在每一次对话轮次后都生成记忆。  
- **显式指令（Explicit Command）**：通过用户的直接命令触发记忆生成（例如，“记住这一点”）。

选择何种触发机制涉及**成本与保真度之间的权衡**：

- **高频生成**（如实时模式）可确保记忆高度详细且新鲜，捕捉对话中的每一个细微之处。但这种方式带来的大模型（LLM）调用和数据库存储成本最高，若处理不当还可能引入延迟。
- **低频生成**（如仅在会话结束时生成）则更具成本效益，但可能导致记忆保真度下降，因为模型需要一次性总结大量对话内容。

此外，需注意避免记忆管理器重复处理相同事件，否则将带来不必要的开销。

## 记忆即工具（Memory-as-a-Tool）

一种更高级的方法是**让智能体自主决定何时创建记忆**。在此模式中，记忆生成被封装为一个可供调用的**工具**（例如 `create_memory`），该工具的定义应明确哪些类型的信息值得持久化。

### 背景操作 vs. 阻塞操作  

**记忆生成** 是一项开销较大的操作，需要调用大语言模型（LLM）并执行数据库写入。对于生产环境中的智能体（agent），记忆生成几乎**始终应作为后台异步任务处理**。

在智能体向用户返回响应后，记忆生成流程可以并行运行，而不会阻塞用户体验。这种解耦机制对于保持智能体的快速响应至关重要。如果采用**阻塞式（同步）方法**——即用户必须等待记忆写入完成才能收到回复——将导致难以接受的延迟，带来糟糕的使用体验。

因此，记忆生成必须在一个**架构上独立于智能体核心运行时的服务中进行**。

---

### 记忆检索  

在建立了记忆生成机制之后，下一步的关键任务是**记忆检索**。一个智能化的检索策略对智能体的整体性能至关重要，涉及两个核心决策：**应该检索哪些记忆？何时进行检索？**

检索策略的选择在很大程度上取决于记忆的组织方式：

- 对于**结构化的用户画像**（如用户档案），检索通常是简单的查找操作，例如获取完整档案或某个特定属性。
- 而对于**记忆集合**（collection of memories），检索则成为一个复杂的搜索问题。其目标是从大量非结构化或半结构化数据中，发现最相关、概念上最贴近的信息。

本节所讨论的策略，正是为解决**记忆集合的复杂检索挑战**而设计的。

**记忆检索**会在当前对话中搜索最相关的记忆。有效的检索策略至关重要：提供无关的记忆会混淆模型，降低回应质量；而找到恰到好处的上下文，则可能带来极为智能的交互体验。

核心挑战在于：在严格的延迟预算内，平衡记忆的“有用性”。先进的记忆系统超越了简单的关键词搜索，会从多个维度对潜在记忆进行评分，以找出最佳匹配：

- **相关性（语义相似性）**：该记忆在概念上与当前对话有多相关？  
- **时效性（基于时间）**：该记忆是何时生成的？越近越好。  
- **重要性（显著性）**：该记忆整体上有多关键？与相关性不同，“重要性”通常在记忆生成时就已定义。

仅依赖向量相似度是一种常见误区。虽然语义相似度高的记忆可能在概念上接近，但可能是陈旧或无关紧要的。最有效的策略是**综合评分法**——将上述三个维度的得分结合起来进行判断。

对于准确性要求极高的应用，可通过**查询重写**、**重新排序**或**专用检索器**等方法进一步优化检索效果。然而，这些技术计算成本高，会显著增加延迟，因此不适用于大多数实时场景。

当确实需要使用复杂算法，且记忆内容不会快速过期时，引入**缓存层**是一种有效的缓解方案。缓存可以临时存储昂贵的检索结果，在后续遇到相同请求时直接复用，从而避免重复的高延迟开销。

通过**查询重写**（query rewriting），可以利用大语言模型（LLM）来优化搜索查询本身。这包括将用户模糊的输入重写为更精确的查询，或将单个查询扩展为多个相关查询，以捕捉主题的不同方面。尽管这种方法显著提升了初始搜索结果的质量，但它会在流程开始时增加一次额外的LLM调用延迟。

在**重排序**（reranking）中，首先通过相似性搜索检索出一组广泛的候选记忆（例如前50个结果）。然后，使用LLM对这个较小的结果集进行重新评估和重新排序，从而生成更准确的最终结果列表²⁴。

此外，还可以通过微调训练一个**专用的检索器**（specialized retriever）。然而，这种方法需要标注数据的支持，并可能显著增加成本。

归根结底，最佳的检索策略始于更高质量的记忆生成。确保记忆库内容优质且不含无关信息，是保证任何被检索出的记忆都有助于对话的最有效方式。

### 检索时机

检索的最后一个架构决策是：**何时**进行记忆检索？

一种方法是**主动检索**（proactive retrieval），即在每一轮对话开始时自动加载记忆。这种方法能确保上下文始终可用，但对于不需要访问记忆的对话轮次，则会引入不必要的延迟。由于在单轮对话中记忆保持不变，因此可以高效地缓存这些记忆，以降低性能开销。

## 带记忆的推理  

在检索到相关记忆后，最后一步是将这些记忆有策略地插入模型的上下文窗口中。这一过程至关重要——记忆的放置方式会显著影响大语言模型（LLM）的推理能力、运行成本，并最终决定最终回答的质量。

记忆主要通过两种方式呈现：**附加到系统指令中**，或**注入对话历史**。实践中，混合策略通常最为有效：

- 使用 **系统提示（system prompt）** 放置稳定、全局性的记忆（例如用户画像），这类记忆应在整个对话过程中始终存在。
- 对于短暂、片段化且仅与当前对话情境相关的记忆，则使用 **对话注入（dialogue injection）** 或 **记忆作为工具（memory-as-a-tool）** 的方式。

这种方法在保持持久上下文的同时，也兼顾了即时信息检索的灵活性。

## 第64页：程序性记忆

本文白皮书主要聚焦于**陈述性记忆**，这一侧重点也反映了当前商业记忆领域的主流格局。大多数记忆管理平台同样以声明式架构为核心，在提取、存储和检索“**是什么**”（即事实、历史和用户数据）方面表现出色。

然而，这些系统并非为管理**程序性记忆**而设计——后者是提升智能体工作流与推理能力的关键机制。存储“**如何做**”并不只是一个信息检索问题，而是一个**推理增强**问题。管理和维护这种“知道怎么做”的知识，需要一套完全独立且专业化的算法生命周期，尽管其高层结构与声明性记忆类似<sup>26</sup>：

1. **提取（Extraction）**  
   程序性记忆的提取需要专门设计的提示（prompts），旨在从一次成功的交互中提炼出可复用的**策略**或“操作手册”，而不仅仅是记录某个事实或有意义的信息。

2. **巩固（Consolidation）**  
   声明性记忆的巩固侧重于合并相关事实（“是什么”），而程序性记忆的巩固则专注于对工作流程本身（“如何做”）进行整理与优化。这是一个主动的逻辑管理过程，目标包括：
   - 将新的成功方法整合进现有的“最佳实践”；
   - 修复已知计划中的缺陷步骤；
   - 删除过时或无效的操作流程。

3. **检索（Retrieval）**  
   其目的不是为了回答问题而去检索数据，而是为了获取一个能够指导智能体执行复杂任务的**行动计划**。因此，程序性记忆的数据结构可能与声明性记忆有显著不同。

智能体通过程序性记忆实现自身逻辑“自我进化”的能力，自然引发人们将其与一种常见的适应方法进行比较：**微调**（fine-tuning）——通常通过**基于人类反馈的强化学习**（RLHF）来实现<sup>27</sup>。虽然这两种过程都旨在改进智能体的行为，但它们的作用机制截然不同：

## 测试与评估

现在你已经构建了一个具备记忆能力的智能体，接下来应通过全面的质量和评估测试来验证其行为表现。对智能体记忆能力的评估是一个多层次的过程，需要从以下几个方面进行验证：

- **记忆内容的质量**（质量）：智能体是否记住了该记的内容？  
- **记忆的可检索性**（检索）：在需要时能否成功找到相关记忆？  
- **记忆的实际效用**（任务成功率）：使用这些记忆是否真正帮助智能体完成了目标任务？

尽管学术界更关注可复现的基准测试，工业界的评估重点则在于记忆功能如何直接影响生产环境中智能体的性能与可用性。

### 记忆生成质量

记忆生成质量的评估指标用于衡量记忆内容本身的有效性，回答核心问题：“**智能体是否记住了正确的事情？**”

通常通过将智能体生成的记忆与人工构建的“黄金标准记忆集”进行对比来实现评估。

- **精确率（Precision）**：  
  智能体创建的所有记忆中，有多少比例是准确且相关的？高精确率可以防止记忆系统过于“积极”，避免向知识库中引入无关噪声。

- **召回率（Recall）**：  
  在所有本应从源信息中记住的相关事实中，智能体实际捕获了多少比例？高召回率确保智能体不会遗漏关键信息。

- **F1分数（F1-Score）**：  
  精确率和召回率的调和平均值，提供一个综合、平衡的质量度量指标。

## 记忆检索性能  

**记忆检索性能指标**用于评估智能体在正确时间找到正确记忆的能力。  

- **Recall@K**：当需要某条记忆时，正确的记忆是否出现在前 K 条检索结果中？这是衡量检索系统准确性的主要指标。  
- **延迟（Latency）**：记忆检索处于智能体响应的“关键路径”上。整个检索过程必须在严格的延迟预算内完成（例如，低于200毫秒），以避免影响用户体验。  

## 端到端任务成功率  

**端到端任务成功指标**是最终的检验标准，回答核心问题：“记忆是否真正帮助智能体更好地完成任务？” 该指标通过评估智能体在下游任务中的表现来衡量其使用记忆的效果，通常借助一个大语言模型（LLM）“裁判”将智能体的最终输出与标准答案进行比较。裁判判断智能体的回答是否准确，从而有效衡量记忆系统对最终结果的贡献程度。  

## 持续优化的评估机制  

评估不是一次性事件，而是推动持续改进的引擎。上述指标提供了识别系统弱点所需的数据，并支持对记忆系统进行系统性优化。这一迭代过程包括：  
1. 建立基线（baseline）  
2. 分析失败案例  
3. 调优系统（如优化提示词、调整检索算法）  
4. 重新评估以衡量变更的影响  

## 生产就绪性：性能与可扩展性  

尽管上述指标聚焦于质量，但生产环境下的可用性还依赖于**性能表现**。在每个评估维度中，都必须测量底层算法的延迟及其在负载下的扩展能力：  
- **“关键路径”上的记忆检索**通常有严格的亚秒级延迟要求。  
- **生成与整合（Generation and Consolidation）**虽然通常是异步执行，但也必须具备足够的吞吐量以满足用户需求。  

### 结论  
一个成功的记忆系统必须兼具**智能性、高效性和鲁棒性**，才能胜任真实场景的应用。

### 生产环境中的记忆系统考量  

除了性能之外，将具备记忆能力的智能体从原型阶段推进到生产环境时，还需重点关注企业级架构问题。这一转变带来了对**可扩展性**、**弹性**和**安全性**的关键要求。一个可用于生产的系统不仅需要具备智能能力，更需达到企业级的稳健性。

为了确保用户体验不会因计算成本高昂的记忆生成过程而受阻，健壮的架构必须将**记忆处理逻辑**与**主应用逻辑**解耦。尽管这本质上是一种事件驱动模式，但通常通过直接的、非阻塞式 API 调用一个专用的记忆服务来实现，而非依赖自建的消息队列。整个流程如下：

1. **智能体推送数据**：  
   在发生相关事件后（例如一次会话结束），智能体应用会向记忆管理器发起一个非阻塞的 API 调用，将原始数据（如对话记录）“推送”至记忆管理器进行后续处理。

2. **记忆管理器后台处理**：  
   记忆管理服务立即确认请求，并将生成任务放入其内部托管的队列中。随后，该服务独立承担异步的繁重工作——调用必要的大语言模型（LLM）来提取、整合和格式化记忆内容。根据策略，管理器可能会在用户持续不活跃一段时间后才开始处理这些事件。

3. **持久化存储记忆**：  
   服务将最终生成的记忆（可能是新增条目或对已有记忆的更新）写入专用的、持久化的数据库中。对于托管型记忆管理器而言，存储功能通常是内置集成的。

4. **智能体检索记忆**：  
   主智能体应用可在需要为新用户交互提供上下文时，直接查询该记忆存储系统以获取所需信息。

此架构确保了系统的响应性和可维护性，同时支持大规模部署下的高效记忆管理。

# 上下文工程：会话与记忆（2025年11月） 第68页

这种基于服务、非阻塞的方法确保了内存流水线中的故障或延迟不会直接影响面向用户的應用，从而使系统具备更强的弹性。这也影响了在**在线**（实时）生成与**离线**（批量）处理之间的选择：前者适用于保持对话的新鲜度，后者则适合利用历史数据填充系统。

随着应用规模的增长，记忆系统必须能够处理高频事件而不发生故障。面对**并发**请求时，当多个事件尝试修改同一段记忆，系统必须防止死锁或竞争条件的发生。可以通过使用事务型数据库操作或乐观锁机制来缓解竞争问题；然而，这可能在多个请求试图修改相同记忆时引入**排队**或**限流**。

一个强大的消息队列对于缓冲大量事件至关重要，可防止记忆生成服务因负载过高而崩溃。同时，记忆服务还必须具备应对瞬态错误的能力（**故障处理**）。如果某次大语言模型（LLM）调用失败，系统应采用带指数退避的重试机制，并将持续失败的请求路由到死信队列中进行后续分析。

对于全球范围部署的应用，记忆管理器必须使用支持内置**多区域复制**的数据库，以确保低延迟和高可用性。客户端侧的复制不可行，因为记忆整合需要一个单一的、事务一致的数据视图来避免冲突。因此，记忆系统必须在内部处理复制逻辑，向开发者呈现一个统一的逻辑数据存储，同时保证底层知识库在全球范围内的一致性。

托管式记忆系统（如 Agent Engine Memory Bank）应能帮助你解决这些生产环境中的实际问题，使你可以专注于核心智能体逻辑的开发。

## 隐私与安全风险  

记忆来源于用户数据，并包含其中的信息，因此必须实施严格的隐私和安全控制措施。一个恰当的类比是：将系统的记忆视为由专业档案管理员维护的安全企业档案库，其职责是在保护公司利益的同时保存有价值的知识。

该档案库的核心原则是**数据隔离**。正如档案管理员绝不会混杂不同部门的机密文件一样，系统中的记忆也必须在用户或租户层面进行严格隔离。服务于某一用户的智能代理绝不能访问其他用户的记忆信息，这一点需通过严格的访问控制列表（ACL）加以强制执行。

此外，用户必须能够以编程方式控制自己的数据，明确拥有选择不生成记忆、或要求从档案库中删除其所有文件的权利。

在归档任何文档之前，档案管理员都会执行关键的安全步骤：

1. **敏感信息脱敏**：逐页仔细审查内容，去除敏感的个人身份信息（PII），确保知识得以保存的同时不会带来法律或安全风险。
2. **识别并剔除伪造内容**：档案管理员受过训练，能识别并丢弃伪造或蓄意误导的文件——这是防范“记忆投毒”（memory poisoning）的重要防线。同样地，系统在将信息写入长期记忆前，必须对其进行验证与净化处理，防止恶意用户通过提示注入（prompt injection）污染代理的持久性知识。

为此，系统应部署如 **Model Armor** 等防护机制，在信息存入长期记忆前完成验证与清理工作。

此外，若多个用户共享同一组记忆（例如用于指导操作的“程序性记忆”），则存在数据泄露（exfiltration）的风险。例如，当一个用户的程序性记忆被用作另一个用户的参考示例时（类似于在全公司范围内分享备忘录），档案管理员必须首先进行彻底的匿名化处理，以防敏感信息跨越用户边界泄漏。

### 结论  

本白皮书探讨了**情境工程**这一学科，聚焦其两个核心组成部分：**会话（Sessions）** 与 **记忆（Memory）**。从一次简单的对话交互，到生成可持久化、可操作的智能信息，整个过程都由这一实践所驱动——即动态整合所有必要信息（包括对话历史、记忆内容以及外部知识），并将其注入大语言模型（LLM）的上下文窗口中。

这一过程依赖于两个既独立又紧密关联的系统之间的协同作用：即时性的**会话**系统与长期性的**记忆**系统。

- **会话**掌控“当下”，作为单次对话的低延迟、按时间顺序排列的信息容器。其主要挑战在于**性能**与**安全性**，要求实现**低延迟访问**和**严格的隔离机制**。为避免上下文窗口溢出及响应延迟，必须采用诸如基于token的截断或递归摘要等**提取技术**，对会话历史或单个请求负载中的内容进行**压缩处理**。此外，安全至关重要，在持久化会话数据前必须执行**个人身份信息（PII）脱敏**。

- **记忆**则是实现**长期个性化**的核心引擎，也是跨多个会话保持状态持续性的关键机制。它超越了传统的RAG（检索增强生成）模式——RAG使智能体成为“事实”的专家，而记忆则使其成为“用户”的专家。记忆本质上是一个由LLM驱动的主动式ETL（抽取、转换、加载）流水线，负责信息的**提取、整合与检索**。在**提取**阶段，系统将对话历史中最关键的信息提炼为若干核心记忆点；随后通过**整合**过程，将新信息与已有知识库进行融合，消除矛盾、删除冗余，确保知识体系的一致性与精炼性。为了保障流畅的用户体验，记忆的生成应作为**异步后台任务**运行，在智能体完成回复后自动执行。同时，通过追踪信息**来源（provenance）** 并建立防范机制（如抵御记忆污染等风险），开发者能够构建出值得信赖、具备自适应能力的智能助手，真正实现伴随用户不断学习与成长。
